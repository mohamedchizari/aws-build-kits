# Kit B: retrieval over the federal AI use case inventory, a grounding guardrail, and a measured evaluation

First run: read `START_HERE.md`, one page with every command in order.

**Nothing in this kit has been run against AWS.** It was written without an AWS account. No AWS call was run. The first time you run it is the first time it meets the real service, so expect to fix things. Section 8 says exactly what was checked and how.

**Unofficial.** This is a personal demonstration built on public data from the Office of Management and Budget (OMB). It is not endorsed by OMB or by any agency, and it is not an official source for anything in the inventory.

## 1. What this is

A set of numbered scripts that let one person, alone, in their own AWS account:

1. build a small corpus from the OMB 2025 Federal Agency AI Use Case Inventory (400 one-page text documents by default, each with a metadata file);
2. build a fixed evaluation set of 120 questions whose answers are copied from the inventory's own CSV cells (100 answerable, 20 with no answer in the corpus);
3. load the corpus into an Amazon Bedrock knowledge base and watch the ingestion job;
4. create a Bedrock Guardrail that has only a contextual grounding check;
5. run every question (retrieve, generate, check grounding, judge) and get one table: retrieval hit rate, answer correctness by exact match and by a judge model, what the guardrail blocked, and the cost. With the default models the judge is an Amazon Nova model grading an Amazon Nova generator, and the retrieval is hybrid search with the service-managed re-ranker. The table says both;
6. delete everything and check that nothing is left.

Design choices, and why:

- **Knowledge base type: Bedrock Managed Knowledge Base** (`KB_TYPE=managed`). AWS manages the index, so there is no vector store in your account to forget. A second path, `KB_TYPE=s3vectors`, builds a customer-managed knowledge base on Amazon S3 Vectors. It exists as a fallback and because it shows the teardown trap first-hand (the vector bucket outlives the knowledge base). There is no OpenSearch path, on purpose.
- **Retrieval is the service default, said out loud.** For a managed knowledge base AWS says "Retrieval always uses hybrid search, which combines keyword and semantic search" and "Reranking is enabled by default using a service-managed reranking model" [S7]. The kit sends `rerankingModelType: MANAGED` explicitly and prints it in the results, so the hit rate you get is "hybrid search plus the managed re-ranker". It is not a plain vector-search number, and the kit does not compare re-ranking on against off.
- **The kit runs its own evaluation loop** instead of a Bedrock RAG evaluation job. The loop is four API calls per question (`Retrieve`, `Converse`, `ApplyGuardrail`, `Converse` for the judge) and all scoring is plain Python that is unit-tested offline. A managed evaluation job would add AWS's built-in judge metrics (correctness, completeness, helpfulness, logical coherence, faithfulness, citation precision and coverage, harmfulness, stereotyping, refusal; context relevance and coverage for retrieve-only jobs), a report in the console, and no loop to maintain. It would also need a prompt file in S3, another IAM role and an output bucket, and it does not do exact-match checks against known answers. Its retrieve-and-generate job type is configured through `retrieveAndGenerateConfig`; the API reference says the `RetrieveAndGenerate` API "cannot be used with managed knowledge bases" [S34]. Whether the evaluation job has the same limit was not checked (section 2, item 6).
- **Guardrail off and on are compared on the same answer.** Each question is answered once. "Off" is that answer. "On" is the same answer after `ApplyGuardrail`: if the guardrail intervenes, the answer counts as blocked. The two columns therefore differ only by the guardrail. The guardrail is not attached to the generation call itself.
- **Models: Amazon Nova Lite generates, Amazon Nova Pro judges.** Both are Amazon models, so they need no AWS Marketplace subscription and no Anthropic first-time-use form. The price of that convenience: the judge is from the same model family as the generator, and a judge can favour answers written in its own family's style (section 2, item 9). Both ids are configurable.

## 2. Problems first

Every price below was read on 2026-10-07. Region is US East (N. Virginia), us-east-1, unless the line says otherwise. Sources are numbered in section 9.

1. **Untested against AWS.** Request shapes are checked against the API model inside boto3 1.43.108, which catches a wrong parameter name, type or allowed value. It does not catch what only the service knows: permissions, limits, free-form fields, timing. Run every script with `--dry-run` first, then `50_run_eval.py --limit 5` before the full set.

2. **The billing trap this kit avoids: OpenSearch Serverless.** A knowledge base can use an OpenSearch Serverless collection as its vector store. Price: $0.24 per OCU-hour for indexing and for search [S27]. The pricing page says "You will be billed at least for a minimum of 2 OCUs ... for the first collection in an account" for Classic collections [S28]. That is 2 x $0.24 x 24 h = $11.52 a day, about $345.60 in 30 days, with zero queries. (The same page says NextGen collections have no minimum and scale to zero after 10 minutes idle.) This kit never creates a collection. `00_check.py` and `99_verify_clean.py` list every collection in the account and Region and print a loud warning. Do not create this kit's knowledge base in the console with an OpenSearch vector store.

3. **Deleting a knowledge base does not delete its vector store or your S3 bucket.** AWS: "the vector store itself is not deleted if you delete a knowledge base or data source resource" [S8]. `90_teardown.py` deletes each thing separately and `99_verify_clean.py` checks. With `KB_TYPE=managed` there is no vector store resource in your account; the page says nothing specific about managed knowledge bases, so check the bill the next day.

4. **Managed Knowledge Base storage bills until you delete it.** "$5.00 per GB of raw data / month"; managed parsing, embeddings and re-ranking $0 [S26]. The table states no Region and no minimum, and these rows are not in the us-east-1 price list files, so proration and any minimum are unconfirmed. If billed pro rata, the default corpus (0.37 MB of text) is about $0.002 a month.

5. **`Retrieve` is the largest line of an evaluation run on a managed knowledge base.** "$1.00 per 1,000 API calls" [S26]: 120 questions = $0.12. Estimate for one full run with the defaults, list price:

   | Item | Basis | Estimate |
   |---|---|---|
   | Retrieve | 120 calls x $1.00 per 1,000 [S26] | $0.12 |
   | Contextual grounding check | about 720 text units x $0.10 per 1,000 [S24][S26] | $0.07 |
   | Judge, Amazon Nova Pro | about 48,000 input + 3,600 output tokens at $0.80 / $3.20 per 1M [S24] | $0.05 |
   | Generation, Amazon Nova Lite | about 171,000 input + 6,000 output tokens at $0.06 / $0.24 per 1M [S24] | $0.01 |
   | S3 uploads | 800 PUT requests at $0.005 per 1,000 [S29] | under $0.01 |
   | Total for one run | | about $0.25 |

   Token counts assume 4 characters per token. That is an assumption of this kit, not an AWS figure. `50_run_eval.py` prints this estimate before it starts (with `--no-guardrail` without the grounding line: about $0.18) and, afterwards, the cost computed from the token and text-unit counts AWS returned. What that figure leaves out, bad news first: a call that failed or was cut off before its answer arrived (by an error, by Ctrl-C or by a kill), and the second sending of a call the SDK retried, which is counted once. Whether AWS bills those is not known to this kit, and the usage line of `summary.md` says so in every run. Everything else is counted, in every attempt: also the calls that were answered for a question that then failed or was interrupted and that `--resume` ran again. Since round 4 the script notes each answered call of the question in flight in `last_question_calls.json`, and `--resume` turns the note into an "interrupted" row of `raw.jsonl`. If the process is killed in the instant between an answer and that note, the one call is missing without a warning; if the note cannot be read, the usage line says NOT COUNTED and for how many questions. The bill is the only real number.

6. **`RetrieveAndGenerate` cannot be used with a managed knowledge base.** The API reference says: "This API cannot be used with managed knowledge bases. Use AgenticRetrieveStream or Retrieve with managed knowledge bases." [S34]. The AWS sample notebook says the same [S31]. This kit calls neither `RetrieveAndGenerate` nor `AgenticRetrieveStream`: it uses `Retrieve` and then `Converse`, which works the same way for both knowledge base types. Not checked: whether a Bedrock RAG evaluation job of the retrieve-and-generate type runs against a managed knowledge base.

7. **The grounding check will block some correct answers.** It scores grounding (is the answer supported by the passages) and relevance (does it address the question) and blocks below a threshold [S14]. AWS documents it for summarisation, paraphrasing and question answering, not for conversational chat, with limits of 100,000 characters of source, 1,000 of query and 5,000 of answer [S14]. The default thresholds of 0.7 are the ones the AWS sample uses, not tuned values. The results table counts blocks of correct answers, of wrong answers, of invented answers and of plain refusal sentences separately so you can see the trade. The kit asks for the full output (`outputScope: FULL` [S13]) so that the two scores are recorded for answers that pass as well; whether they come back that way is one of the things the first run will show.

8. **Exact match can miss a correct answer. It is built not to credit a wrong one, and it counts what it could not read.** Bad news first: it has credited answers a person would reject. The fourth review wrote 300 more answers and three of them, built only from words on the list, got credit. Two are refused now. One is still credited: "It was reported, is the answer the Environmental Protection Agency", a question in the word order of a statement. On those 300 it now gives credit to 1 of the 111 a person would reject (3 before) and scores 73 of the 189 a person would accept as not correct (85 before). On the second review's 250 answers written to break it, it now scores 61 answers wrong that a person would accept (53 of 121 answerable ones, 8 of 11 refusals). That is the price of that review's main finding: before, it gave credit to 38 of those 250 answers that a person would reject. Now it gives credit to none of them. Round 4 changed neither count. The numbers are in section 8 and in `REVIEW_NOTES_r4.md`.

   How it reads an answer (`kitlib/scoring.py`, one block, written out). It is an allow-list. An answer earns credit only if, once these are taken out:

   - the question's own words: the use case name, "reported by the <agency>" as the question words it, and the question itself when the answer repeats it word for word;
   - the two citation marks the prompt shows the model, `[1]` and `(document uc-0001)`;
   - the name of the field where it holds the words of a value ("stage of development", "high-impact determination", "high-impact status");
   - exactly one accepted spelling of the expected value;

   every word that is left is on one short list of 53 phrases. For every question: "the", "it", "is", "it's", "its", "this", "is a", "is an", "as a", "as an", "answer", "use case", "ai use case", "named", "recorded", "recorded for", "recorded as", "listed as", "given as", "for the", "for this", "in the", "inventory", "federal", "2025", and "according to" followed by "the inventory", "the record", "the passage", "the passages", "the document", "the documents", "passage" or "document". For an agency question also: "agency", "reporting", "was", "reported", "reported by", "that reported", "U.S.", "United States". For a stage question: "stage", "stage of development", "development stage", "has been". For a high-impact question: "determination", "high-impact determination", "high-impact determinations", "high-impact status", "yes", "determined to be", "was determined to be", "has been determined to be". There is no single "a", "to", "be", "of", "by", "not" or "was" (outside agency questions) on the list: alone they build "is to be Deployed" and "a use case of the agency". Since round 4 a second list of 37 phrases (`LEAD_IN_PHRASES`) is accepted in the same way, for every question: "based on", "per", "stated in" and "as stated in", each followed by one of the eight sources that "according to" takes, and "as of the", "sure", "has a", "classified as", "listed under". The number in "passage 1" or "document 2" is read as a citation mark, and "of" is accepted in one place: between the name of the field and the value ("a stage of development of Deployed"). The words of a phrase must stand apart: "was_determined to be" is not the phrase "was determined to be".

   Anything else makes the answer **unclear**:

   - any other word. So every negation, hedge and change of tense ("not", "probably", "will be", "formerly", "yet to be"), every comparison ("rather than", "instead of", "other than", "unlike"), a bureau name, an explanation, a date;
   - any character other than letters, digits, white space and `. , ; : " ' ( ) * _ -`, the backtick, and the typographic forms of the quotation marks and the hyphen. So a question mark, a slash, an equals sign, a table. An exclamation mark is read as a period where it ends a sentence ("Deployed!") and is refused anywhere else ("!=");
   - a second, different value of the field anywhere in the answer, also when it is the one being denied ("Deployed (not Retired)"). Since round 4 the same value written two or three times counts once ("Deployed." as a first line and then the sentence); four times or more is unclear;
   - text in quotation marks that is neither the question's use case name nor a value: another use case (`named "AI Use Case Inventory"`);
   - a sentence that starts with "is", "was", "has" or a like verb, or holds one of them directly before "it", "this" or "that": a question without its question mark ("Is it Deployed"). A sentence also starts after a semicolon;
   - a value with "it", "this", "that", "the" or "its" directly after it: a verb with an object, not a value ("It deployed the use case").

   Unclear counts as NOT correct and has a row of its own in the table, so you see how many answers the rule could not read. A clean statement of another value of the field is counted in a third row. Correct, unclear, another value and refused add up to the answerable questions. In `per_question.csv`, `exact_note` says which rule decided and `exact_unread` holds the words or characters that were on no list.

   Accepted spellings of a value: the value as the CSV writes it, in any case, and "Predeployment". Between two words of a value only what the value has there may stand, or a space: where it has a hyphen, a space or one hyphen ("Pre deployment", "High - impact"); where it has a comma, the comma or a space; where it has a space, only a space. So "not, High-impact" is no longer read as the value "Not High-impact" (it was until round 4). For an agency also: the full name followed by its own abbreviation, as the documents write it ("Department of State (STATE)", also with the name in bold), and since round 4 the abbreviation followed by the full name in brackets ("VA (Department of Veterans Affairs)") and "Department of Treasury" for "Department of the Treasury"; the abbreviation alone in upper case, unless it is also a US state code or an ordinary word (of the 41 abbreviations in the CSV, VA, ED, STATE, DOC, DOT, DOE and SEC count only next to the full name; the other 34 count alone); and for the 14 "Department of X" agencies, "X Department" and "Dept. of X", plus "X" alone when X is two words or more ("Veterans Affairs", "Health and Human Services"; never "Energy" or "State"). These 32 short names were checked against all 41 agency names in the CSV, not only the 31 a question asks about: none is part of another agency's name, and "The State Department of Transportation" is not read as the Department of State. The list of ordinary words is hand-written for this CSV; `20_build_eval_set.py` prints which abbreviations it rules out and writes every accepted spelling into `eval_set_meta.json`. A JSON answer counts in one form only: one object, one key from a short list (`{"agency": "..."}`, `{"stage_of_development": "..."}`, `{"high_impact_determination": "..."}` and seven more keys), the value a string. No table and no other key-value form counts.

   A refusal is the fixed sentence "I cannot answer this from the inventory documents provided." and nothing else: the answer must equal it once white space around it and one final period are trimmed. No character is stripped and no case is folded, so the sentence in quotation marks, in lower case, with an apology in front or with anything after it is not a refusal. An answer that holds the sentence next to a value is unclear.

   The ten most common shapes of an answer a person would accept that exact match now scores not correct (counts on the reader's 250):

   | Shape | Lost | Example |
   |---|---|---|
   | A second value of the field in the answer, also when it is denied, past, or about another use case | 14 | "Retired. It was previously Deployed." |
   | An explanation, a gloss, a date or a condition added to the value | 12 | "As of May 2025 it is Deployed." |
   | A hedge | 7 | "It is probably the Environmental Protection Agency." |
   | The bureau or office named with the agency | 7 | "Environmental Protection Agency (EPA), Office of Mission Support." |
   | The refusal sentence with anything added or changed | 5 | "I'm sorry, but I cannot answer this from the inventory documents provided." |
   | An agency abbreviation alone that is also a word or a state code, or not in upper case | 4 | "VA", "The SEC.", "epa" |
   | A table | 3 | "\| Stage of development \| Deployed \|" |
   | A paraphrase or another form of the value | 3 | "The use case is being piloted.", "It isn't high-impact." |
   | A refusal in other words | 3 | "I don't know." |
   | A one-word short name of an agency | 2 | "Energy", "Treasury" |

   The eleventh shape, a JSON value that is not a string (`{"high_impact": true}`), was lost once. The same answers pasted whole are lost too: an answer that copies the entire source document is unclear, because the document holds values of other fields.

   What it still cannot do. It reads words, not meaning. "No false credit" was measured on 520 hand-written answers (section 8); it is not proved, and an answer built only from list words that a person would still reject is possible: the fourth review found three, and one of them is still credited (top of this item). It checks the value, not where the model got it: "Deployed" is credited whatever passage the model read, which is what the hit-rate rows are for. And because the list is short, a model that explains, hedges or names the bureau will lose credit on answers that are right. If the unclear row is large, read those rows and quote the judged number with it, not the exact-match number alone.

9. **The judge is a language model from the same family as the generator, and its reply is read by words, not by meaning.** With the defaults an Amazon Nova judge (Nova Pro) grades an Amazon Nova generator (Nova Lite). A judge can favour answers written in its own family's style. `summary.md` states the two families at the top: SAME FAMILY, SAME PROVIDER, "different families" (printed only when both model ids name a known provider and the two differ), or COULD NOT TELL when an id cannot be read. Set `JUDGE_MODEL_ID` to another family if you can (Anthropic models need a one-time use-case form [S20]).

   Round 5, bad news first. The fifth review showed that the round 4 reader still gave credit that a reply's own reason takes back, in plain wording: 16 of 16 DECLINED replies whose reason says the candidate gave a value ("The candidate's answer contains a budget figure that the documents lack."), and 9 of 9 CORRECT replies whose second sentence contradicts the reference ("The candidate matches the reference. The impact is high." for "Not High-impact"). It also lost 7 of 16 ordinary refusals ("The candidate uses the refusal sentence."). What changed, with the question known: under DECLINED, every clause whose subject is the candidate (or its answer, response or reply) must be a refusal (declines, cannot answer, gives no answer, uses the refusal sentence, says that the documents do not hold it), so "contains a budget figure", "reports the budget amount" and "is an agency" are refused; a sentence that gives something ("a budget figure is given", "the agency is in the answer", "the figure it found") is refused; every sentence must say something negative or be plain ("This is the expected behaviour."); and the judge's own "the documents lack it" no longer counts as the candidate declining. Under CORRECT, a word of a stage or high-impact value that stands outside the reference value and outside a field name ("the impact is high", "is in development", "is in use") refuses the verdict, in every kind of question. Nine words joined `JUDGE_REFUSAL_WORDS` and "which is correct" after a refusal is no longer read against it. The reader's cases now: 0 of 16, 0 of 9 and 0 of 7 wrong, its 46 controls kept. The fixer's own replies, written before they were run: 30 of 30 such DECLINED replies refused (round 4: 5) and 25 of 25 ordinary refusals read (round 4: 15; the first draft of round 5: 29 and 22); a second set written after that draft, 43 of 46 read as a person reads them (40 on its first run, 27 by the round 4 reader). Without the question nothing changed. All of it is hand-written text; the rules read sentence shapes, not meaning. The record is `REVIEW_NOTES_r5.md`.

   Round 4, bad news first. The fourth review showed that the reader described below still gave credit to verdicts that their own reason takes back: on 203 hand-labelled replies, 30 with the question and 37 without; 58 of 82 replies that name another value the way people write it ("Energy", "the State Dept", "piloting"); 37 of 60 with one ordinary mismatch phrase ("is inconsistent with", "!="). Five of the 30 were read as CORRECT only because the round 3 fix takes the quoted reference out. What changed: when the question is known, which it always is in a run, the reason of a CORRECT or DECLINED verdict is read by allow-list, as an answer is. Once the quoted values are taken out, every word of it must be one of the question's own words or on a written-out list (`JUDGE_TIE_WORDS` and `JUDGE_PRO_FORMS`, 185 and 57 words, for CORRECT; `JUDGE_REFUSAL_WORDS`, 175, for DECLINED), a CORRECT reason must hold the reference value or a word of agreement, and what it says of the candidate must lead to the reference. A one-word agency name with a capital letter, an abbreviation in any case and another form of a stage word count as a value. Without the question no value is known; there the lists of words that speak against a verdict got longer (`JUDGE_MISMATCH_WORDS`, 109 patterns) and what the reply says of the candidate is compared with what it says of the reference. The same 203 replies now: 0 read flatteringly with the question, 2 without; 0 of 82 and 0 of 60 either way. The price is the other direction: a clear verdict whose reason uses a word on no list is counted as unparseable, 27 of that reader's 123 clear verdicts with the question (32 before) and 45 without (49 before). These counts on the 203, 82 and 60 replies were measured before round 5; those sets are not in the kit and were not read again, and the round 5 rules can have moved the counts with the question both ways (they refuse more, and they read refusals that were lost). The rules, every list, every count and the replies still misread are in `REVIEW_NOTES_r4.md`.

   The reply is read as CORRECT or DECLINED, the two verdicts that give the system credit, only when it states exactly one verdict and nothing else in the reply speaks against it. A verdict is stated by: a JSON object with a "verdict" key (a capitalised key, single quotes, a comma before the closing brace, a period after the word and one level of nesting are tolerated; next to the verdict the object may carry a reason and a confidence, nothing else); JSON cut off after a complete verdict pair; a line "Verdict: CORRECT" (or "The verdict is CORRECT."); or the word at the very start of the reply, alone or followed by a dash, a colon or a period and a reason. Then the whole rest of the reply is read: the reason, other keys, other objects, the text before and after. CORRECT is refused when any of it holds one of 59 patterns (`CONTRADICTS_CORRECT`: "incorrect", "declin...", "not", "no", "wrong", "differ...", "another", "but", "however", "if", "only", "?" and the like). A negation is let through only together with the bad thing it denies: "no fact that contradicts it", "does not decline", "not a refusal", "nothing incorrect", "no errors", and also "different wording". Any other "not" or "no" still refuses the verdict. DECLINED is refused when the text holds "correct", "wrong", "answered", "names", "states" or "says" followed by anything but a refusal, "but", "then", "does not decline", "not a refusal" and the like, or when it gives a reason that does not say the candidate declined (since round 4, with the question known, "the information is not available in the passages" and the like count as saying so; since round 5 only where the candidate is said to say it, and what the reason says of the candidate must be a refusal). So "not correct", "PARTIALLY CORRECT", `{"verdict": "CORRECT", "reason": "The candidate is not correct"}`, `{"verdict": "DECLINED", "reason": "The candidate answered Department of Energy"}`, the rubric echoed back, two different verdicts and an empty reply are all counted as unparseable, which is never "correct". `judge_note` in `per_question.csv` says why. For a question that has no answer, only the verdict INCORRECT counts as "answered anyway"; CORRECT or an unparseable reply is shown in its own row as "judge verdict unclear".

   Since the rehearsal on real model text (section 8) the reader is told which question the reply is for. A judge quotes values, and a value can hold a list word: the inventory's own value "Not High-impact" holds "not", and "Presumed High-Impact, but Not High-impact" holds "but". Before the lists are applied, these are taken out of the reply, because the judge did not choose their words: every accepted spelling of the question's reference answer; a value the question itself gives (the agency in "reported by the ..."); the use case name as the question writes it; the question repeated word for word; and the words NO ANSWER, for a question that has none. The candidate's own words are never taken out, not even inside quotation marks, because a quoted answer can hold the very words that speak against the verdict ('Candidate says "The use case is not Deployed."'). Taking words out can only help a verdict, so the same step refuses more than before: CORRECT is refused when the reply names a value of the question's field that is not the reference ("Candidate states Deployed; the reference is Pilot."), and DECLINED when it names any value that is neither the reference nor in the question ("declines, then states Pilot"). A value that is not the reference is never taken out. `scoring.read_judge` called without the question takes nothing out, so there a reason that quotes "Not High-impact" is unparseable, as it was for every such reply before the fix.

   What this cannot do. The check is lists of words, not meaning. With the question known, a reason made only of list words, in a sentence shape the round 5 rules do not know, is read as its verdict even where a person would not accept it: "The candidate gives a stage, and the reference gives a stage too." under CORRECT, and "The candidate's answer is a refusal; its budget figure is not in the documents." under DECLINED ("its" is read as the use case's). The two DECLINED examples this paragraph gave in round 4 ("The candidate declines. The agency is in the answer." and "The candidate has the answer. It declines to say so.") are refused since round 5; without the question they are still read as DECLINED. Read on its own, without the question (only when `scoring.read_judge` is called by hand), more gets through, because no value is known, the round 5 rules are not applied and the lists there only name bad words (the fifth review's DECLINED replies among them): one stated value with nothing to compare it with ("Candidate states Pilot.", "The candidate names the Bureau of Mines."), a comparison without a verb ("Candidate says the Dept. of Energy, reference EPA."), a part of a refusal quoted under CORRECT, and a mismatch phrase on no list ("is a world away from", "garbles"). Three limits of the round 3 reader are caught since round 4: "The candidate says DOE; the reference says EPA." and "No information that it declines." with or without the question, "The candidate names the Bureau of Mines." with it. A reply cut off inside the reason is read by its verdict and by the part of the reason that arrived, and since round 4 `summary.md` carries a WARNING line that counts the answers and judge replies that ended at the token limit. And clear replies are still lost: a sentence instead of a verdict ("The candidate is correct."), "not correct" (not read as INCORRECT), a verdict inside a list, a correct verdict whose reason uses a list word innocently ("only the abbreviation is given"), a reply cut off inside a value ("Candidate correctly states Not"), a CORRECT that quotes or retells a right answer with an innocent list word in it ("no other stage is recorded"), a DECLINED whose reason only repeats the reference ("Reference is NO ANSWER.") and, since round 5, one whose reason says only in the judge's own words that the answer is not there ("The information is not available in the documents."), and, found in round 4: a reason with a word on no list ("Cannot fault it.", "The answer is error-free."), a key next to the verdict that is not a reason or a confidence (`"score": 1`), a verdict line with anything after the word ("Verdict: INCORRECT (the candidate says Pilot)", a check mark), and a pronoun where the value should stand ("Not High-impact is the reference and the candidate states it."). On the round 2 reader's 88 replies, which carry no question: 0 read flatteringly (7 before), 9 lost (22 before), of which 2 of the 39 clear CORRECT replies (14 before); round 4 changed none of these counts. On the 120 replies real models wrote in the rehearsal: 120 read as a blind reader labelled the answers (110 before the fix; the 10 lost were all "Not High-impact"), also after round 4; since round 5 only their five CORRECT wordings were read again (unchanged, a test), the 20 DECLINED replies are not in the kit. A high "could not be parsed" count means the judged column undercounts: read those replies in `raw.jsonl`.

10. **100 questions is a small sample, and the two columns are one sample.** The 95% interval on a rate near 80% from 100 questions is roughly plus or minus 8 points, and the table prints the interval for each rate. Use it to judge how far one rate could move with other questions. Do not use it to compare the "off" and "on" columns: they are the same 100 answers, so their difference is exactly the blocked answers, which the table counts one by one. To compare two separate runs (another top k, another model), count in the two `per_question.csv` files how many questions changed from right to wrong and how many from wrong to right. Overlapping intervals is not the test for answers to the same questions. A handful of changes in each direction is noise.

11. **Model lifecycle.** The model cards list Amazon Nova Lite and Nova Pro as Active, launched 2024-12-05, "EOL no sooner than" 2025-12-05 [S21][S22]. They can be moved to legacy at any time after that date. `00_check.py` prints the lifecycle status.

12. **Permissions.** `30_deploy_kb.py` creates an IAM role and passes it to Bedrock, so your identity needs `iam:CreateRole`, `iam:PutRolePolicy` and `iam:PassRole` [S5]. An AWS Organizations policy can forbid these in a work account. Use a personal account.

13. **Data quality, licence, and what the kit ships.** The corpus is agency-reported text, copied as published, with typos and uneven detail. The OMB repository has no LICENSE file and no licence statement in its README (checked at the pinned commit). The scripts download the CSV to a git-ignored `build/` folder on your machine. The kit itself ships five real rows of it as a test fixture, `tests/fixtures/inventory_5rows.csv`: CSV rows 8, 108, 1687, 2079 and 2647, copied as published except that the `contact_email` cell is blanked. Since the second review it also ships `tests/fixtures/agencies_41.json`: the 41 distinct agency names with their abbreviations (the CSV columns `agency_name` and `agency`), used to test the accepted agency spellings against every agency. No other use case of the data is in the kit; the test answers written for the second review use made-up use case names. The `contact_email` column is never read. One free-text cell of the CSV also holds an e-mail address (row 1396). Every cell the builder reads has e-mail addresses and phone-shaped strings replaced by a marker, and the builder refuses to write a document in which either can still be found. The default 400 documents needed no replacement; a build of every row needs one.

14. **Held-out questions are hard negatives, and near-duplicates are kept out.** Twelve of the unanswerable questions ask about real use cases that were left out of the corpus. A confident wrong answer there is a real failure, not a scoring error. The inventory also holds groups of use cases whose names differ by one word. `20_build_eval_set.py` does not build an answerable question on a document that has a similarly named twin with the same answer (the right answer could then come from the wrong document), and does not build a held-out question on a use case whose agency has a twin of it in the corpus (the "invented" agency could then be the true one). With the default corpus that turns down 6 candidates, which are 5 different CSV rows: row 1088 is turned down for two question types (the script prints both numbers). One question is kept although a similarly named document with another answer is in the corpus; its row carries `near_duplicate_doc_ids`. The thresholds and the rows turned down are in `build/eval/eval_set_meta.json`.

15. **Quotas and throttling.** No quota increase is known to be needed: the run is 120 sequential questions, and the managed knowledge base quota read on 2026-10-07 is 600 `Retrieve` requests per minute per knowledge base [S4]. A new account can still have low per-model token quotas. The SDK retries throttled calls (8 attempts in total); a question that still fails is recorded with its error, left out of every rate, and the run is marked INCOMPLETE until you re-run it with `--resume`.

16. **Three values decide where the scripts act: the account, the Region and the prefix. One of them changing under you is how a teardown deletes nothing and reports success.** An `AWS_REGION` exported in your shell overrides `config.env`, and many setups export one. `.state.json` (local, git-ignored) records the account id, the Region and the prefix of the deploy. Every script that reads it compares all three with your current settings and with the account your credentials belong to, and stops with both values named if one differs. A second deploy somewhere else is refused while the first is still recorded. Only the last four digits of the account id are ever printed.

17. **Rebuilding the corpus after a deploy.** The data source ingests everything under `corpus/` in the bucket. If old documents stayed there after a rebuild, the knowledge base would hold documents the evaluation set believes are absent, and "unanswerable" questions could have an answer. So `30_deploy_kb.py` makes the bucket hold exactly the local corpus before it syncs (it removes its own stale `uc-NNNN` objects and stops if it finds anything else there), and `50_run_eval.py` refuses to run unless the corpus on disk, the evaluation set and the deployed corpus carry the same fingerprint. The sync is what removes the documents from the index ("Document deleted: The document is removed from the vector store" [S36]); that it does so for this corpus was never run. The data source is created with deletion protection off, because with it on "the sync skips its delete phase" when more than the threshold (15% by default) would be deleted [S35].

18. **`--resume` only continues the same run.** A run writes its settings to `run_config.json`: models, top k, guardrail and its thresholds, knowledge base, corpus and evaluation set fingerprints, prompts, `--limit`, the version of the scoring rules and, since round 4, a fingerprint of `build/eval/eval_set_meta.json`, the file that holds the label sets. `--resume` refuses to continue under any other setting, so one table never mixes rows produced in different ways; it also refuses, with a sentence, when `run_config.json` itself cannot be read. A run started before the fifth review cannot be resumed: its rows were scored under older rules (the rules are scoring version `2026-10-08.r5` now). `raw.jsonl` keeps every attempt, one row per physical line whatever text a row holds, with the whole judge reply (until round 4 only its first 500 characters) and the stop reason of the generation and the judge call; a question that was interrupted leaves an "interrupted" row that holds only the usage of the calls that were answered (item 5). `--resume` reads it once, before the first billed call, and the summary is built from those rows and the new ones without reading the file again. If its last row was cut short because the run was stopped while writing it, `--resume` moves the half row to `raw_cut_off_row.txt` and runs that question again. A damaged row anywhere else stops `--resume` before any call and names the line; if you remove that line by hand, its question is run again and the calls it held leave the usage line (since round 5 nothing else changes: the other questions stay finished).

19. **A state file that cannot be read stops everything until you deal with it.** If `.state.json` is cut short, emptied or otherwise not readable, every script stops with the same instructions and exit code 1 (the clean check runs its read-only checks and reports INCOMPLETE at best). No script deletes or overwrites the file: it may be the only record of where the kit was deployed. The way out is in section 5. Do not delete the file to get past the message: with no state file and the wrong Region in your shell, nothing can tell the scripts where to look.

20. **`--limit N` is a smoke test, not a sample.** It takes the first N questions of the file, and the file starts with the 40 agency questions. `summary.md` says "first N of 120 questions (--limit N)". With `--no-guardrail` every cell of the "Guardrail on" column says "not applied".

## 5. Tear it down and prove it

```
python 90_teardown.py --dry-run     # shows every delete call; exit code 5, never 0
python 90_teardown.py               # asks once, then deletes each resource separately
python 99_verify_clean.py           # exit code 0 means clean in the place named on its RESULT line
```

Run these with the same settings and the same credentials you deployed with.

`90_teardown.py` first asks STS which account your credentials belong to and compares the account, the Region and the prefix with `.state.json`. If one differs it stops, deletes nothing and leaves the file as it was (section 2, item 16). Then it deletes, in this order: the data source, the knowledge base, the guardrail, the S3 vector index and vector bucket (only if you used `KB_TYPE=s3vectors`), the IAM role, and the S3 bucket with every object, object version and delete marker in it. The role is deleted only after the data source and knowledge base are gone, so the service can still use it while they are being removed. That order is this kit's precaution, taken from the AWS sample's cleanup order [S31], not a documented rule. If the knowledge bases or their data sources cannot be listed, the script does not know whether one still exists, so it leaves the vector store, the role and the bucket alone and exits 1. It finds resources by `.state.json` and by their fixed names, so a lost state file does not stop it. Afterwards it lists again and takes a resource out of `.state.json` only if that listing shows it gone. Whatever it could not delete or could not list stays recorded. When nothing is left, the place moves to a "history" inside `.state.json`. The script never deletes the state file.

Before it exits, the teardown lists once more, this time under every prefix: every bucket, role, knowledge base, guardrail and vector bucket whose name contains `-fedrag-`, and everything tagged `project=aws-kits` of a kind this kit creates. Bucket and role names carry their Region and are listed from any Region, so a deploy in another Region or under another prefix shows up here. If anything is listed, or a listing fails, the exit code is 1, each item is printed with the settings its name points to (`AWS_REGION=... KIT_PREFIX=...`), and the RESULT line says NOT FINISHED. The script also prints the date and time it finished and how many hours the knowledge base existed (from the creation time `30_deploy_kb.py` recorded).

| `90_teardown.py` exit code | Meaning |
|---|---|
| 0 | Every delete succeeded and the listing afterwards shows no kit B resource. With no state file, the RESULT line says so and says this is not proof for any other Region |
| 1 | Stopped (wrong place, damaged state file, no answer to the question), or something is still recorded or still listed, or a listing failed. Things may be billing |
| 5 | `--dry-run`: the calls were printed and nothing was deleted |

`--region` and `--prefix` name the place on the command line; they take the place of `AWS_REGION` and `KIT_PREFIX` for that run and are compared with a readable state file like any other setting.

`99_verify_clean.py` checks one place per run: the account STS reports, the Region and the prefix in use. Its RESULT line names all three (the account by its last four digits). In that place it lists every S3 bucket, IAM role, knowledge base (with data sources), guardrail and S3 vector bucket whose name contains `-fedrag-`, whatever prefix is in front; anything `.state.json` records by id; every resource in the Region tagged `project=aws-kits`; and every OpenSearch Serverless collection. Every tagged resource counts as left, also one that another kit created, because the tag is shared by the three kits. It reads `.state.json` only to find out whether this was the right place to look, and writes to it only to note that a place in the history was found clean.

| `99_verify_clean.py` exit code | Meaning |
|---|---|
| 0 | CLEAN: nothing found in the place named, every check ran, and `.state.json` names no other place still to check |
| 1 | NOT CLEAN: something is left in the place named |
| 3 | No kit resource, but an OpenSearch Serverless collection exists in the account and Region |
| 4 | INCOMPLETE: a check could not run, or `.state.json` (or its history) names an account, Region or prefix this run did not check, or `.state.json` cannot be read. It prints the settings to run it with |
| 5 | `--dry-run`: the calls were printed and nothing was checked. It is not 0 so that a dry run cannot pass for a clean account |

**What a clean result does not cover.** A clean result covers that one account, Region and prefix. The RESULT line ends with what the state file said about the place: "This is the place .state.json names", or "NO STATE FILE was found, so nothing told this script where the kit was deployed: this is not proof for any other Region, account or prefix" (when the file is there but records nothing, the same warning in other words). In the second case the check is only as good as your memory of where you deployed. What still gives a forgotten deploy away without a state file: a bucket or a role, because their names are listed from every Region. What does not: a guardrail created with `40_create_guardrail.py` alone, or a knowledge base whose bucket and role you already deleted by hand, in another Region. For those the check says CLEAN for the Region it looked in, with the warning in the RESULT line. And a state file that was put back from an older copy is believed as it stands: what you deployed after the copy was made is not in it, and the RESULT line then says "This is the place .state.json names" for the old place, with no warning. The fourth review built that case: a second deploy in another Region, the older file restored, the newer bucket and role deleted by hand, and the knowledge base left there with a CLEAN result.

**If `.state.json` cannot be read** (cut short, emptied, not text). Every script stops and prints the same steps; none deletes or overwrites the file.

1. Open the file in a text editor. What is left of it may still show the Region and the prefix; the scripts print what they can still read in it (the bucket name, `<prefix>-fedrag-corpus-<account>-<Region>`, is the first thing a deploy writes).
2. Tear down by naming the place yourself, once for every Region and prefix you deployed to: `python 90_teardown.py --region <Region> --prefix <prefix>`. With both options the teardown acts on the kit's fixed names there, in the account your credentials belong to, and leaves the damaged file where it is. Its exit code is 1 even when every delete succeeded, and its RESULT line says NOT CONFIRMED: the record of where the kit was deployed could not be read, so the script cannot say that this was the only place.
3. Run `python 99_verify_clean.py` with `AWS_REGION` and `KIT_PREFIX` set to the same place. While the damaged file is in the folder the result is NOT CLEAN or INCOMPLETE, never CLEAN.
4. When step 3 finds nothing in every place you used, move the file out of the folder yourself and run `99_verify_clean.py` once more. It can then say CLEAN for the place it checks, with the "NO STATE FILE" warning.

For a second, independent look that does not rely on this kit's code, run the shared audit: `python ../common/whats_running.py --region <the AWS_REGION in your config.env> --prefix <your KIT_PREFIX>` (see `../common/README.md`).

Then look at the Billing console the next day. Charges already incurred still appear; nothing new should.

## 7. What you can truthfully say afterwards, and what you cannot

You can say these only after you have run the kit yourself and filled in the results, and only with your own numbers:

- "I built retrieval-augmented question answering on Amazon Bedrock Knowledge Bases over N public federal documents, using the managed knowledge base type (or S3 Vectors), in my own account."
- "Retrieval was the managed knowledge base's hybrid search with the service-managed re-ranking model switched on. I sent that setting explicitly and did not compare it with re-ranking off or with another re-ranker." (For `KB_TYPE=s3vectors`: "vector search, no re-ranking model configured".)
- "I measured it on a fixed set of 100 answerable and 20 unanswerable questions whose answers come from the source data. The source document was among the top k passages for X of 100. An exact-match check that gives credit only when the answer is the expected value plus words from a short fixed list scored Y of 100 correct and could not read U of 100, which it counts as not correct. A judge model graded Z of 100 correct. The judge was an Amazon Nova model grading an Amazon Nova generator, so the same model family." Give the 95% intervals with the rates, always give U when you quote Y, and always say the judge sentence when you quote Z. Y and U are the rows "correct by exact match" and "unclear to exact match" of `summary.md`.
- "I added a Bedrock Guardrail contextual grounding check, applied to the same answers, and counted what it changed: it blocked A answers, of which B had been judged correct."
- "The run cost $C at list price by the kit's arithmetic and $D on the bill. I deleted everything, and the clean check reported CLEAN for my account, Region and prefix."
- "I know why I did not use OpenSearch Serverless for a demo, and that deleting a knowledge base does not delete its vector store."
- What failed on first contact with the real service and how you fixed it. That is first-hand experience.

You cannot say:

- That this is production experience, a customer delivery, or a load-tested system. It is one person, one small corpus, sequential requests.
- That it ran in AWS GovCloud or under FedRAMP, or that it meets any federal compliance requirement. It ran in a commercial Region in a personal account.
- That the demo is official, or endorsed by OMB or any agency.
- That you used Bedrock's managed RAG evaluation jobs, agentic retrieval, a re-ranking model you chose or configured, or OpenSearch. The kit uses none of them. Do not say "no re-ranking" either: on the managed type the service's own re-ranker was on.
- That Y is "the accuracy". It is the share of answers that state the expected value in plain words. The U unclear answers may be right or wrong; you know only after reading them, and then you can say how many you found right.
- That the exact-match check is proved never to credit a wrong answer. Of 520 hand-written test answers, 281 were ones a person would reject, and it credited none of them; of 300 more written for the fourth review it still credits 1 of the 111 a person would reject (section 8). That is a measurement on those answers, made without a model.
- That the hit rate is a vector-search or embedding-quality number. On the managed type it is hybrid search plus re-ranking, with AWS's managed embedding model and default chunking.
- That the judged number is an independent grade. With the default models the judge and the generator are from one family. If you changed the judge, say which model judged.
- That the guardrail "prevents hallucination". You counted how often one contextual grounding guardrail (a grounding filter and a relevance filter, each at one threshold) blocked answers on 120 questions. The table does not say which of the two filters blocked.
- That the guardrail made answers better or worse by a measured margin with an interval. The two columns are the same answers; the difference is the count of blocks.
